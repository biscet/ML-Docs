# Выбор checkpoint в разных опытах

«Лучший» означает checkpoint, который выиграл по заданному правилу на
определённой проверке. По ходу истории правило менялось.

| Опыты | Отбор |
| --- | --- |
| Раннее полное обучение, шардовое продолжение, Stage-2, dense8 | Минимальный validation loss |
| Поздние selector и partial-unfreeze запуски | Сначала prefix, затем accuracy, затем selector CE |

Позднее правило лексикографически максимизировало кортеж:

```python
score = (
    metrics["prefix_tokens"],
    metrics["accuracy"],
    -metrics["selector_ce"],
)
```

При равном prefix сравнивали accuracy; при равенстве обоих выбирали меньший
selector CE.

## Почему правило важно

| Запуск | Наблюдавшийся компромисс |
| --- | --- |
| Project v1 | Последняя accuracy выше, но минимум loss выбрал шаг 3,500 |
| Dense8 | У шага 122 префикс длиннее, но loss выбрал шаг 74 |
| Короткий selector-only | CE продолжал снижаться, prefix после выбранного шага 96 ухудшался |
| Долгий selector-run | Лучший prefix вырос при небольшом снижении общей self-conditioned accuracy |
| Продолжение KL | Последние CE и KL ниже, но prefix сохранил экспорт шага 52 |

Снижение дифференцируемого loss не обязательно улучшает дискретный greedy
prefix. Вместе с checkpoint нужно хранить objective, ширину блока, способ
оценки и правило отбора.

## Проверка экспортируемого состояния

Долгий selector-тренер проверял веса в dtype GGUF-экспорта, затем возвращал
FP32 master weights для продолжения оптимизации. При близких logits
округление может менять победивший токен.

Правило по loss и входы наставника разобраны в [выборе Stage-2 checkpoint](checkpoint-selection.md).
Разница между последним и выбранным состоянием описана в [resume и экспортах](resume.md).
