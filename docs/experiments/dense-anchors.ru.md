# Dense8: восемь anchor на ответ

Dense8 стартовал от v1.2.0 и обучал весь draft. Вместо одного случайного anchor
из каждого сохранённого ответа выбирали восемь разных точек.

## Выбор точек и накопление градиента

Допустимый диапазон делили на восемь интервалов и брали по одной точке из
каждого:

```python
size = sequence_length - width - prompt_n + 1
anchors = [
    rng.randrange(prompt_n + i * size // count,
                  prompt_n + (i + 1) * size // count)
    for i in range(count)
]
```

Здесь `count = 8`. Loader требовал достаточной длины для восьми разных anchor.
Окна будущих меток при этом могли пересекаться.

Чтобы не держать все блоки в GPU-памяти одновременно, выполняли восемь
microbatch backward. Loss каждого делили на восемь, затем делали одно
обновление оптимизатора:

$$
L_{\mathrm{update}} = \frac{1}{8}\sum_{r=1}^{8}L_r.
$$

При batch 4 и ширине 4 полный update предъявлял $4\cdot8\cdot3=96$ будущих
меток. Это число предъявлений, а не уникальных токенов корпуса. Больше anchor
даёт больше прямых меток на capture, но требует больше вычислений и повторяет
связанные метки. Подробнее в разделе [усреднения по anchor](../analysis/multi-anchor.md).

## Выполненный прогон

План содержал 600 существующих контекстов, по 300 на язык, и 14 шардов.
Выполнено 12 шардов, 536 контекстов и 134 обновления. Ширина оставалась 4.
Начальный LR составлял 2.5e-6; позже наставник поднял его до 5e-6.

| Метрика | Начало dense8 | Выбранный шаг 74 |
| --- | ---: | ---: |
| Loss | 2.601195 | 2.595146 |
| Token accuracy, прежний способ подсчёта | 62.5651% | 62.6953% |
| Correct-prefix proxy | 1.689453 | 1.705078 |
| Top-16 recall | 84.9609% | 85.2865% |

Отбор ещё шёл по loss. У шага 122 правильный префикс был длиннее, но выбранный
loss оказался у шага 74. Поздние тренеры явно отдавали приоритет
self-conditioned prefix.

Исходники архива: `experiments/02-dense8/scripts/anchor_sampling.py`,
`amp_step.py` и `train_shard.py`.
