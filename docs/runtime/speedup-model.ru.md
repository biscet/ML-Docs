# Почему acceptance не равен ускорению

Обозначим:

- $t_{\mathrm{AR}}$ это время обычного декодирования одного токена;
- $t_{\mathrm{draft}}$ это время предложения блока;
- $t_{\mathrm{verify}}$ это время проверки блока target;
- $t_{\mathrm{overhead}}$ покрывает служебные операции и откат состояния.

Грубая стационарная модель:

$$
\boxed{
\operatorname{Speedup}
\approx
\frac{
\mathbb{E}[L_{\mathrm{cycle}}]\, t_{\mathrm{AR}}
}{
t_{\mathrm{draft}} + t_{\mathrm{verify}} + t_{\mathrm{overhead}}
}
}
$$

## Как читать отношение

Числитель растёт с числом принятых токенов за цикл. Знаменатель растёт со всем, что
понадобилось, чтобы их получить. Draft может угадывать лучше и при этом тратить
слишком много времени. Больший блок может угадать больше токенов и всё равно
оказаться медленнее меньшего: проверка масштабируется с шириной, а длинные блоки
реже выживают целиком.

Формула объясняет компромисс. Исход она не предсказывает. Реальные времена нужно
измерять, для этого и существует [бенчмарк](benchmark.md).

## Два следствия для настройки

- Ширина блока это совместный выбор качества и стоимости, а не ручка качества.
  Расширение двигает оба члена в знаменателе и добавляет bonus-токен только при
  выживании всего блока.
- Улучшение offline-порядка помогает, лишь если удлиняет принятый prefix.
  Точность, набранная после первой ошибки, не двигает
  $\mathbb{E}[L_{\mathrm{cycle}}]$ вообще.
